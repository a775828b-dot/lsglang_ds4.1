# 2026-10-22：Engram NVMe 后端的多卡修正

## 变化

- `adapter/engram_backend.py`：Engram 统计文件按 TP rank 分开写（rank 0 仍是 `layer-N.json`，其余是 `layer-N-rankK.json`）。
  以前各 rank 写同一个文件名，改名时会互相抢，抢输的一方抛 FileNotFoundError，它的统计线程（以及同一线程里的 scale 常驻触发）就此退出。
  scale 常驻前的内存检查改按本 rank 的行数计算。
- `adapter/row_store.cpp` / `librow_store.so`：scale 常驻（`row_store_preload_scales`）只读本 rank 负责的行段，查表时下标按行段起点换算；
  以前每个 rank 都读整张 scale 表（每层 2.86 GiB）。
- 单卡时行为不变：行段就是整张表，读的字节、下标和内存占用都和以前一样。

## 验证（单卡机器上模拟多卡）

本机只有一张卡，用 CPU 模拟，不建 CUDA 上下文：真实后端按 (tp_size, rank) 初始化，直接调用读盘函数（生产里由 CUDA 主机回调调用的就是它），
按 Lsglang 的 TP 规则判定：本 rank 的行等于权重文件的字节，其余行为 0，各 rank 相加等于全归约的结果。
两层 Engram，每层 4222 个 id（4000 个随机、22 个在分段边界上、200 个重复）：

| | 本 rank 的行与文件一致 | 其余行为 0 | 第二遍（走行缓存）一致 | 各 rank 相加与文件比 |
|---|---|---|---|---|
| TP=1 | ✓ | — | ✓ | 逐位一致 |
| TP=2 | ✓ | ✓ | ✓ | 数值一致（个别 −0 变成 +0，真实全归约也一样） |
| TP=4 | ✓ | ✓ | ✓ | 同上 |

- scale 常驻（第 1 层，整表 2.861 GiB）：TP=1 每卡 2.861 GiB，TP=2 每卡 1.431 GiB，TP=4 每卡 0.715 GiB；
  预载后首次查询（scale 走常驻表）与文件 0 处不一致。
- 统计文件：两个进程模拟两张卡同时写，各写各的文件，没有异常。修改前的写法在紧循环里各写 2 万次，约一半抛 FileNotFoundError。

## 生产复核（单卡）

重启后两层 scale 常驻仍是整表（3,072,049,344 / 3,072,133,456 字节）；照抄测试单请求、两个请求各 4 段，0 处错字
（单请求有 1 段结尾多抄了一个 `</src>`，是固定验证下已知的现象）。

## 没有覆盖到

第二张卡上的 CUDA 部分（主机回调、拷贝、gather、NCCL 全归约）和 DS 管线其余部分仍未在真实多卡上运行过；本仓库的启动脚本仍是单卡。
